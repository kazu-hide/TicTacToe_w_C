# ミニプロジェクト: 2人チャット（5時間）

五目並べを一旦離れて、ネットワーク部分だけを小さなプログラムで先に体得する。

`LEARNING_STEPS.md` の Step 1〜3 に相当する内容を、ゲームロジックの都合を一切気にせず扱う。

---

## なぜ先にチャットを作るのか

Step 1〜3 には**五目並べ固有の要素が1つも無い**。やっていることは「行を送る」「行を受け取る」「両方を同時に待つ」だけで、これはそのままチャットの仕様そのもの。

先にチャットで作っておく利点:

- Step 0（既存コードのリファクタ）を後回しにできる。あのステップは既存コードの状態しだいで所要時間が読めず、しかもネットワークの学習にはならない
- 五目並べの盤面表示や手番管理と混ざらないので、通信のバグが通信のバグとして見える
- **リファクタ後の完成形を先に知った状態で Step 0 に臨める**。何のためにどう分けるのかが体験として分かっているので、リファクタの判断が速くなる

---

## 使い捨てにしないこと（重要）

これは練習用の別プロジェクトではあるが、**書いたコードの大半は五目並べにそのまま移す**。そのため、ファイル名と関数シグネチャを `NETWORK_DESIGN.md` に合わせて書く。

```
chat/
  linebuf.c / linebuf.h    → 五目並べへ 100% そのまま移植
  net.c     / net.h        → net_connect の中身がほぼそのまま移植
  main.c                   → poll ループの構造が移植（中身は書き換え）
  Makefile
```

五目並べ側で新たに書くことになるのは `game.c`、`ui.c`、プロトコルの解釈部分だけ。**通信の土台はこの5時間で完成する。**

### 最初に用意するもの

```makefile
CC     = cc
CFLAGS = -std=c11 -Wall -Wextra -g -fsanitize=address,undefined
SRCS   = main.c net.c linebuf.c

chat: $(SRCS)
	$(CC) $(CFLAGS) $(SRCS) -o $@

clean:
	rm -f chat
```

サニタイザは最初から有効にしておく。ネットワークコードはバッファ操作が多く、境界のミスが起きやすい。実行時に検出してくれる価値は、わずかな速度低下を大きく上回る。

# Session 1: 接続を確立する（80分）

## 到達点

```
$ ./chat --host 8080
peer connected
peer says: hello from join

$ ./chat --join 127.0.0.1:8080
connected
peer says: hello from host
```

固定の挨拶を1行だけ交換して両方終了する。まだチャットではない。

## やること

- [ ] `net.h` に構造体と `net_connect` を定義する
- [ ] host 側: `getaddrinfo`(AI_PASSIVE) → `socket` → `setsockopt(SO_REUSEADDR)` → `bind` → `listen` → `accept`
- [ ] join 側: `getaddrinfo` → `socket` → `connect`
- [ ] 接続後、固定文字列を1行 `send` する
- [ ] 相手からの1行を `recv` して表示し、終了する（**この時点では雑でよい。行の切り出しは Session 2 でやる**）

```c
/* net.h — 五目並べでもこのシグネチャをそのまま使う */
typedef enum { NET_LISTEN, NET_CONNECT, NET_RELAY } net_mode_t;

typedef struct {
    net_mode_t  mode;
    const char *host;      /* CONNECT のとき接続先 */
    const char *port;
    const char *room;      /* RELAY 用。今回は未使用 */
} net_config_t;

/* 接続済みの fd を返す。失敗なら -1 */
int net_connect(const net_config_t *cfg);
```

`NET_RELAY` は今回使わないが、enum に入れておく。後で Phase 2 を実装するとき、呼び出し側を一切変えずに済む。

## 要点

**`getaddrinfo` は「候補のリスト」を返す。** ホスト名の解決、IPv4/IPv6 の両対応、サービス名の解決をまとめて行い、試すべきアドレスを複数返す。順に試して最初に成功したものを使うのが正しい作法。

`AF_UNSPEC` にしておくと IPv4 と IPv6 の両方が候補に入る。ここを `AF_INET` と決め打ちすると、後で IPv6 直接接続を試すときに書き直しになる。

**`SO_REUSEADDR` は必須。** 無いと Ctrl+C で止めた直後の再起動が `bind` 失敗する。開発中に何十回も遭遇する。

**戻り値を必ず見る。** ネットワーク系のシステムコールは日常的に失敗する。`connect` の戻り値を無視すると、繋がっていないソケットに書き込んで原因不明の挙動になる。

## 動作確認は `nc` で

自作の両側でデバッグすると、どちらが悪いか分からない。片方を `nc` に置き換える。

```
# join 側だけを検証
$ nc -l 8080
$ ./chat --join 127.0.0.1:8080

# host 側だけを検証
$ ./chat --host 8080
$ nc 127.0.0.1 8080
```

## 実験: TIME_WAIT を見る（10分）

1. `setsockopt(SO_REUSEADDR)` の行をコメントアウトしてビルド
2. `--host 8080` で起動 → `nc` で繋ぐ → Ctrl+C で止める
3. すぐ `--host 8080` を再起動 → `bind` が失敗するのを確認
4. `ss -tan | grep 8080` で `TIME_WAIT` を目で見る
5. 60秒ほど待つと成功するようになるのを確認
6. コメントアウトを戻す

`TIME_WAIT` は「遅れて届いたパケットが次の接続に混入するのを防ぐ」ための待機状態。バグではなく設計。`SO_REUSEADDR` はそれを承知で再バインドを許可するオプション。

## 詰まりやすい点

- サーバー側の `getaddrinfo` は第1引数 `NULL` + `AI_PASSIVE`
- `accept` の戻り値をリスニングソケットの変数に上書きしてしまう（別の fd。リスニング側は開いたまま）
- ポート番号を `int` で渡そうとする（`getaddrinfo` は文字列を取る）
- `freeaddrinfo` の呼び忘れ

## 完了条件

`--host` と `--join` を別端末で起動し、双方に相手の挨拶が表示される。

## 理解度チェック

- `listen` した fd と `accept` が返す fd は何が違うか
- `AF_UNSPEC` にすると候補が複数返る。全部試す必要があるのはなぜか

# Session 2: 行の切り出し（120分・本体）

## 到達点

相手が1バイトずつ細切れに送ってきても、複数行をまとめて送ってきても、正しく行単位で表示できる。

## 学ぶこと

**TCP はバイトストリームであり、メッセージの境界を保存しない。**

Session 1 で挨拶が1回の `recv` で取れたのは、短くてたまたま1回で届いただけ。以下はすべて起こりうる。

- 1行が2回以上の `recv` に分割される
- 2行が1回の `recv` にまとめて届く
- 行の途中で `recv` が返る

「1回 `send` したら相手も1回 `recv` で受け取れる」という直感は **UDP のもの**。TCP が保証するのは「送った順序でバイトが届く」ことだけ。

この誤解はローカルの小さいデータでは表面化せず、実ネットワークや負荷がかかったときに壊れる。だから意識的に実験して体で覚える。

## まず実験する（40分）

**コードを書く前に、壊れることを確認する。**

### 実験1: 分割して届く

Session 1 のコードに、1バイトずつ送るデバッグモードを足す。

```c
/* デバッグ用: 意図的に細切れで送る */
for (size_t i = 0; i < len; i++) {
    send(fd, buf + i, 1, 0);
    usleep(100000);          /* 100ms */
}
```

受信側は `recv` するたびに戻り値をログに出す。

```c
ssize_t r = recv(fd, tmp, sizeof tmp, 0);
fprintf(stderr, "[recv] %zd bytes: %.*s\n", r, (int)r, tmp);
```

`recv` が 1 バイトずつ何度も返るのが見える。「`recv` の内容 = 1メッセージ」と書いたコードはここで壊れる。

### 実験2: まとめて届く

送信側で `hello\nworld\n` を1回の `send` で送る。`recv` が1回で両方を返すのを確認する。行で切り出していなければ `world` を取りこぼす。

### 実験3: パケットを直接見る

```
$ sudo tcpdump -i lo -A -n port 8080
```

ループバック上を流れたバイト列がそのまま見える。TCP セグメントの区切りとアプリのメッセージの区切りが無関係であることの、決定的な証拠になる。

**この3つを見てから実装に入る。**先に正解のコードを書くと、なぜその形なのかが身につかない。

## 実装する（80分）

- [ ] `linebuf_t` を定義する
- [ ] `recv` したデータをバッファ末尾に追加する
- [ ] バッファ内に `\n` がある間、行を1本ずつ取り出してコールバックへ渡す
- [ ] 取り出した分をバッファ前方へ詰め直す（`memmove`）
- [ ] 末尾の `\r` を除去する
- [ ] バッファが満杯なのに `\n` が無ければエラーとして切断する

```c
/* linebuf.h — 五目並べへそのまま移植する */
typedef struct {
    char   buf[1024];
    size_t len;
} linebuf_t;

typedef void (*line_cb_t)(const char *line, void *ctx);

/* fd から読めるだけ読み、完成した行ごとに cb を呼ぶ。
 * 戻り値:  1 = 継続, 0 = 相手が切断, -1 = エラー */
int linebuf_feed(linebuf_t *lb, int fd, line_cb_t cb, void *ctx);
```

実験1のデバッグモードを有効にしたまま動かして、正しく行が組み立てられるようになったら成功。

## 詰まりやすい点

- **`\n` を含まない残りを捨ててしまう**。次の `recv` と繋げる必要がある。ここが本質
- `memcpy` を使う（領域が重なるので未定義動作。`memmove` が正しい）
- `recv` が返したバッファを文字列として扱う。**NUL 終端されていない**。長さを持ち回るか明示的に終端を置く
- `recv` の第3引数に `sizeof lb->buf` を渡す（正しくは `sizeof lb->buf - lb->len`）。オーバーフローする。サニタイザを有効にしていれば即座に検出される

## 完了条件

実験1（1バイトずつ送信）を有効にしたまま、受信側が行を正しく組み立てて表示する。

## 理解度チェック

- `recv` の戻り値と「送信側が `send` を呼んだ回数」に関係はあるか
- なぜ 1024 バイトの上限を設けて超えたら切断するのか。無制限に伸ばすと何が起きるか
- `memmove` で詰め直す代わりに、読み出し位置を示すインデックスを持つ実装も可能。どちらが良いか

# Session 3: poll で双方向にする（80分）

## 到達点

両側から自由に打ち込めて、相手の発言がリアルタイムに表示される、普通のチャット。

## まず失敗を体験する（15分）

Session 2 のコードに、素朴に `fgets` で入力を読むループを付ける。

```c
while (1) {
    fgets(line, sizeof line, stdin);   /* ここでブロックする */
    send(fd, line, strlen(line), 0);
    linebuf_feed(&lb, fd, on_line, NULL);
}
```

この状態で相手側を Ctrl+C で終了させる。こちらは `fgets` で止まったままなので**何も起きない**。何か打ち込むまで、相手がいなくなったことに気づけない。相手の発言も、こちらが1行打つまで表示されない。

これが `poll` が必要な理由。

## 実装する（65分）

`poll` は「監視したい fd の配列」を渡し、どれかが準備できるまで待つ。標準入力もれっきとした fd（`STDIN_FILENO` = 0）なので、ソケットと並べて監視できる。

```c
struct pollfd pfds[2] = {
    { .fd = STDIN_FILENO, .events = POLLIN },
    { .fd = sock,         .events = POLLIN },
};

for (;;) {
    int rc = poll(pfds, 2, 1000);          /* 1000ms でタイムアウト */
    if (rc < 0) {
        if (errno == EINTR) continue;      /* シグナルで中断。異常ではない */
        break;
    }
    if (rc == 0) continue;                 /* 定期処理の置き場（今回は空） */

    if (pfds[1].revents & (POLLHUP | POLLERR)) { /* 切断 */ break; }
    if (pfds[1].revents & POLLIN) { /* 相手の発言 */ }
    if (pfds[0].revents & POLLIN) { /* 自分の入力 */ }
}
```

- [ ] `fgets` を捨て、`poll` ループへ移行する
- [ ] **標準入力側にも `linebuf_t` を使う**（`read(0, ...)` で読む。Session 2 の実装をそのまま流用できる）
- [ ] `POLLHUP` / `POLLERR` を切断として扱う
- [ ] `EINTR` を握りつぶさず continue する

## 要点

**タイムアウト引数（第3引数）の意味。** `-1`（無限待ち）にすると、何も届かない間はコードが一切動かない。有限値にすると `rc == 0` の分岐が定期的に回るので、後で PING や持ち時間の更新をそこに置ける。今回は空でよいが、**この分岐は最初から用意しておく**（五目並べの Step 9 でここに書く）。

**`EINTR` の扱い。** シグナルが届くと `poll` は `-1` / `errno == EINTR` を返す。エラーではないので継続する。見落とすと、ターミナルのリサイズなどで唐突に終了する。

**`events` と `revents` は別物。** `events` は監視したいイベントで自分が設定する。`revents` は実際に起きたイベントで `poll` が設定する。`POLLHUP` / `POLLERR` は `events` に指定しなくても `revents` には現れる。

**標準入力にも `linebuf_t` を使うのがコツ。** `fgets` と `read` を混在させると挙動が読みにくくなる。両方を同じ仕組みで扱えば、コードが対称になって理解しやすい。

## 詰まりやすい点

- `poll` の第2引数は監視する fd の数。配列の確保数ではない
- 自分の入力途中に相手の発言が届いて表示が混ざる。今回は気にしない（改行して表示し直す程度で十分）
- `read(0, ...)` が 0 を返すのは EOF（Ctrl+D）。切断と同じ扱いにする

## 完了条件

両側から自由に打ち込めて、片方を Ctrl+C で終了させると即座にもう片方が検知して終了する。

## 理解度チェック

- `poll` のタイムアウトを `-1` にすると、将来ハートビートをどこに書けなくなるか
- `events` に `POLLHUP` を指定しなくてよいのはなぜか

# 予備枠: 仕上げ（20分）

- [ ] `main` の先頭に `signal(SIGPIPE, SIG_IGN)` を入れる
- [ ] `recv` の戻り値 0（正常切断）と負（エラー）を区別する
- [ ] 送受信した行を `stderr` にトレース出力する

```c
fprintf(stderr, "%s %s\n", is_send ? ">>" : "<<", line);
```

```
$ ./chat --join 127.0.0.1:8080 2> trace.log
```

**`SIGPIPE` の無視は必須。** 相手が既に閉じた接続に `send` すると、デフォルトではプロセスが即死する。エラーメッセージも出ないので初見では原因が分からない。無視しておけば `send` が `-1` / `errno == EPIPE` を返し、通常のエラー処理で扱える。

トレースログは実装コストに対して効果が非常に大きい。**五目並体でも Step 1 の時点で入れる。**

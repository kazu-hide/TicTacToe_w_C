# ネットワーク基礎ミニプロジェクト: 2人チャット（3時間）

五目並べを一旦離れて、**ネットワークの基礎を3時間で体得する**ための実習。
題材は1対1のチャットだが、目的はチャットを作ることではなく、以下の3つを身につけること。

---

## 到達目標

このドキュメントを終えたとき、次のことが「説明できて」「書ける」状態になっている。

| # | 到達目標 | 確認方法 |
|---|---|---|
| 1 | ソケット接続の確立手順を、サーバ側とクライアント側の違いを含めて説明できる | Session 1 の理解度チェック |
| 2 | **TCP がバイトストリームであり、メッセージ境界を保存しない**ことを、自分で再現できる | Session 2 の実験1・2 |
| 3 | 受信バイト列から行を切り出すバッファを、分割・結合の両方に耐える形で実装できる | Session 2 の完了条件 |
| 4 | `poll` で複数の入力を同時に待つ理由と書き方を説明できる | Session 3 の理解度チェック |

**2 が最重要。** ここだけは時間をかける。他は落としても後で取り返せるが、これは誤解したまま進むと後の全てが壊れる。

## なぜチャットから始めるのか

五目並べにネットワーク対戦を入れる場合、通信部分でやることは「行を送る」「行を受け取る」「両方を同時に待つ」の3つだけで、**ここに五目並べ固有の要素は1つも無い**。

先にチャットで作る利点は3つ。

1. **バグの切り分けが楽** — 盤面表示や手番管理と混ざらないので、通信のバグが通信のバグとして見える
2. **完成形を先に知った状態で本体のリファクタに臨める** — [#30](https://github.com/kazu-hide/TicTacToe_w_C/issues/30)（ゲームコアと I/O の分離）が「何のために必要か」を体験として理解した後に着手できる
3. **書いたコードの大半をそのまま移せる**（後述）

---

## 使い捨てにしないこと

練習用の別プロジェクトではあるが、**書いたコードの大半は五目並べにそのまま移す。**

```
chat/
  linebuf.c / linebuf.h    → 五目並べへ 100% そのまま移植
  net.c     / net.h        → net_connect の中身がほぼそのまま移植
  main.c                   → poll ループの構造が移植（中身は書き換え）
  Makefile
```

五目並べ側で新たに書くのは、ゲーム状態の同期とプロトコルの解釈だけになる。**通信の土台はこの3時間で完成する。**

# 事前準備（10分・3時間の外）

学習対象ではない定型部分。写して動けばよい。

## ディレクトリと Makefile

```console
$ mkdir chat && cd chat
```

```makefile
CC     = cc
CFLAGS = -std=c11 -Wall -Wextra -g -fsanitize=address,undefined
SRCS   = main.c net.c linebuf.c

chat: $(SRCS)
	$(CC) $(CFLAGS) $(SRCS) -o $@

clean:
	rm -f chat
```

**サニタイザは最初から有効にする。** ネットワークのコードはバッファ操作が多く、境界のミスが起きやすい。実行時に即座に検出してくれる価値は、わずかな速度低下を大きく上回る。Session 2 で必ず助けられる。

> **Linux で動かす場合のみ**: glibc では `-std=c11` を指定すると POSIX の宣言（`getaddrinfo` / `poll` / `usleep`）が隠れてコンパイルエラーになる。`-std=gnu11` にするか `-D_POSIX_C_SOURCE=200809L` を足す。macOS では `-std=c11` のままで問題ない（確認済み）。

## 引数パース

`main.c` の骨組み。ここは学習対象ではないので、そのまま使ってよい。

```c
#include <stdio.h>
#include <string.h>
#include "net.h"

int main(int argc, char **argv) {
    net_config_t cfg = {0};

    if (argc == 3 && strcmp(argv[1], "--host") == 0) {
        cfg.mode = NET_LISTEN;
        cfg.port = argv[2];
    } else if (argc == 3 && strcmp(argv[1], "--join") == 0) {
        /* "127.0.0.1:8080" を host と port に割る */
        static char buf[256];
        snprintf(buf, sizeof buf, "%s", argv[2]);
        char *colon = strrchr(buf, ':');
        if (!colon) { fprintf(stderr, "usage: %s --join HOST:PORT\n", argv[0]); return 1; }
        *colon = '\0';
        cfg.mode = NET_CONNECT;
        cfg.host = buf;
        cfg.port = colon + 1;
    } else {
        fprintf(stderr, "usage: %s --host PORT | --join HOST:PORT\n", argv[0]);
        return 1;
    }

    int fd = net_connect(&cfg);
    if (fd < 0) return 1;

    /* ここから先を Session 1 以降で書く */
    return 0;
}
```

`strrchr`（最後の `:` を探す）を使っているのは、IPv6 アドレス `::1:8080` を考慮するとポートは末尾側にあるため。

# Session 1: 接続を確立する（50分）

## この回の1つの大きな考え

> **サーバとクライアントは対称ではない。** サーバは「待ち受ける窓口」と「個別の通話路」という2つのソケットを持つ。

## 到達点

```console
# 端末1
$ ./chat --host 8080
peer connected
peer says: hello from join

# 端末2
$ ./chat --join 127.0.0.1:8080
connected
peer says: hello from host
```

固定の挨拶を1行だけ交換して両方終了する。まだチャットではない。

## 予想を書く（3分）

実装の前に、次の2つに答えを書いてみる。あとで答え合わせをする。

- サーバ側とクライアント側で、呼ぶ関数はどう違うと思うか
- サーバが `accept` で受け取るものは何だと思うか

## 実装する（30分）

### net.h

```c
#ifndef NET_H
#define NET_H

/* 五目並べでもこのシグネチャをそのまま使う */
typedef enum { NET_LISTEN, NET_CONNECT, NET_RELAY } net_mode_t;

typedef struct {
    net_mode_t  mode;
    const char *host;      /* CONNECT のとき接続先 */
    const char *port;
    const char *room;      /* 中継サーバ用。今回は未使用 */
} net_config_t;

/* 接続済みの fd を返す。失敗なら -1 */
int net_connect(const net_config_t *cfg);

#endif
```

`NET_RELAY` は今回使わないが enum に入れておく。後で中継サーバを実装するとき、呼び出し側を一切変えずに済む。

### 手順

- [ ] **host 側**: `getaddrinfo`(`AI_PASSIVE`) → `socket` → `setsockopt(SO_REUSEADDR)` → `bind` → `listen` → `accept`
- [ ] **join 側**: `getaddrinfo` → `socket` → `connect`
- [ ] 接続後、固定文字列を1行 `send` する
- [ ] 相手からの1行を `recv` して表示し、終了する
      （**この時点では雑でよい。行の切り出しは Session 2 でやる**）

`getaddrinfo` の使い方の骨格:

```c
struct addrinfo hints;
memset(&hints, 0, sizeof hints);
hints.ai_family   = AF_UNSPEC;      /* IPv4 でも IPv6 でもよい */
hints.ai_socktype = SOCK_STREAM;    /* TCP */
hints.ai_flags    = AI_PASSIVE;     /* サーバ側のみ。第1引数 NULL と組で使う */

struct addrinfo *res;
int rc = getaddrinfo(NULL, cfg->port, &hints, &res);
if (rc != 0) {
    fprintf(stderr, "getaddrinfo: %s\n", gai_strerror(rc));
    return -1;
}

for (struct addrinfo *p = res; p; p = p->ai_next) {
    /* 順に試し、成功したら break */
}
freeaddrinfo(res);
```

## 説明

**`getaddrinfo` は「候補のリスト」を返す。** ホスト名の解決、IPv4/IPv6 の両対応、サービス名の解決をまとめて行い、試すべきアドレスを複数返す。順に試して最初に成功したものを使うのが正しい作法。

`AF_UNSPEC` にしておくと IPv4 と IPv6 の両方が候補に入る。ここを `AF_INET` と決め打ちすると、後で IPv6 で繋ごうとしたときに書き直しになる。

**`SO_REUSEADDR` は必須。** 無いと Ctrl+C で止めた直後の再起動が `bind` に失敗する。開発中に何十回も遭遇する。

```c
int yes = 1;
setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &yes, sizeof yes);
```

**戻り値を必ず見る。** ネットワーク系のシステムコールは日常的に失敗する。`connect` の戻り値を無視すると、繋がっていないソケットに書き込んで原因不明の挙動になる。失敗時は `perror("connect")` で理由を出す癖をつける。

## 動作確認は `nc` を相棒にする

自作の両側でデバッグすると、どちらが悪いか分からない。**片方を `nc` に置き換える**と切り分けが一瞬で終わる。

```console
# join 側だけを検証（相手は nc に任せる）
$ nc -l 8080
$ ./chat --join 127.0.0.1:8080

# host 側だけを検証
$ ./chat --host 8080
$ nc 127.0.0.1 8080
```

これは**この先ずっと使うデバッグ手法**なので、ここで身につけておく。

## 実験A: TIME_WAIT を見る（10分）

> **問い**: サーバを Ctrl+C で止めた直後に再起動すると、なぜ `bind` が失敗するのか。

**予想を書いてから**進む。

1. `setsockopt(SO_REUSEADDR)` の行をコメントアウトしてビルド
2. `--host 8080` で起動 → 別端末から `nc 127.0.0.1 8080` で繋ぐ → Ctrl+C で止める
3. すぐ `--host 8080` を再起動 → `bind` が失敗するのを確認
4. 状態を目で見る

```console
$ netstat -an | grep 8080
tcp4  0  0  127.0.0.1.8080   127.0.0.1.54321   TIME_WAIT
```

5. 60秒ほど待つと成功するようになるのを確認
6. コメントアウトを戻す

**答え**: `TIME_WAIT` は「遅れて届いたパケットが、同じアドレスの組み合わせで張られた次の接続に混入するのを防ぐ」ための待機状態。バグではなく設計。`SO_REUSEADDR` はそれを承知の上で再バインドを許可するオプション。

> **macOS 注意**: `ss` コマンドは Linux 専用で macOS には存在しない。上記のとおり `netstat -an | grep 8080` を使う。どのプロセスが掴んでいるかまで見たい場合は `lsof -nP -i :8080`。

## 詰まりやすい点

- サーバ側の `getaddrinfo` は第1引数 `NULL` + `AI_PASSIVE`。ここにホスト名を書かない
- **`accept` の戻り値を、リスニングソケットの変数に上書きしてしまう。** これは別の fd。リスニング側は開いたままにする
- ポート番号を `int` で渡そうとする（`getaddrinfo` は**文字列**を取る）
- `freeaddrinfo` の呼び忘れ（サニタイザが検出してくれる）

## 完了条件

`--host` と `--join` を別端末で起動し、双方に相手の挨拶が表示される。

## 理解度チェック

1. `listen` した fd と `accept` が返す fd は何が違うか
2. `AF_UNSPEC` にすると候補が複数返る。全部試す必要があるのはなぜか

# Session 2: TCP はバイトストリーム（85分・本体）

## この回の1つの大きな考え

> **TCP が保証するのは「送った順序でバイトが届くこと」だけ。** メッセージの区切りは保証しない。区切りはアプリが自分で作る。

## よくある誤解（名指しで潰す）

> ❌ 「1回 `send` したら、相手も1回の `recv` で同じ内容を受け取れる」

これは **UDP の性質**であって TCP ではない。TCP では以下が全て起こりうる。

- 1行が2回以上の `recv` に分割される
- 2行が1回の `recv` にまとめて届く
- 行の途中で `recv` が返る

Session 1 で挨拶が1回の `recv` で取れたのは、**短くてたまたま1回で届いただけ**。

この誤解はローカルの小さいデータでは表面化せず、実ネットワークや負荷がかかったときに壊れる。だから意識的に実験して体で覚える。

## 実験する（25分）

**コードを書く前に、壊れることを確認する。**

### 実験1: 分割して届く（10分）

> **問い**: 送信側が `hello\n` を1バイトずつ6回に分けて送ったら、受信側の `recv` は何回返るか。

**予想を書く。**

Session 1 のコードに、1バイトずつ送るデバッグモードを足す。

```c
/* デバッグ用: 意図的に細切れで送る */
#include <unistd.h>   /* usleep */

for (size_t i = 0; i < len; i++) {
    send(fd, buf + i, 1, 0);
    usleep(100000);          /* 100ms */
}
```

受信側は `recv` するたびに戻り値をログに出す。

```c
ssize_t r = recv(fd, tmp, sizeof tmp, 0);
fprintf(stderr, "[recv] %zd bytes: %.*s\n", r, (int)r, tmp);
```

`recv` が1バイトずつ何度も返るのが見える。**「`recv` の内容 = 1メッセージ」と書いたコードはここで壊れる。**

### 実験2: まとめて届く（10分）

> **問い**: `hello\nworld\n` を1回の `send` で送ったら、受信側は何回の `recv` で受け取るか。行で切り出していないコードはどう壊れるか。

**予想を書く。**

実行すると `recv` が1回で両方を返す。行で切り出していなければ `world` を取りこぼす（あるいは `hello\nworld` を1メッセージとして扱ってしまう）。

### 実験3（任意・5分）: パケットを直接見る

```console
$ sudo tcpdump -i lo0 -A -n port 8080
```

ループバック上を流れたバイト列がそのまま見える。TCP セグメントの区切りとアプリのメッセージの区切りが無関係であることの、決定的な証拠になる。

> **macOS 注意**: ループバックインタフェースは `lo` ではなく **`lo0`**。`-i lo` は失敗する。

**この実験は時間が無ければ飛ばしてよい。** 実験1と2で結論は既に出ている。

## 実装する（60分）

- [ ] `linebuf_t` を定義する
- [ ] `recv` したデータをバッファ末尾に追加する
- [ ] バッファ内に `\n` がある間、行を1本ずつ取り出してコールバックへ渡す
- [ ] 取り出した分をバッファ前方へ詰め直す（`memmove`）
- [ ] 末尾の `\r` を除去する（Windows 由来の相手や `telnet` は `\r\n` を送ってくる）
- [ ] バッファが満杯なのに `\n` が無ければエラーとして切断する

```c
/* linebuf.h — 五目並べへそのまま移植する */
#ifndef LINEBUF_H
#define LINEBUF_H
#include <stddef.h>

typedef struct {
    char   buf[1024];
    size_t len;
} linebuf_t;

typedef void (*line_cb_t)(const char *line, void *ctx);

/* fd から読めるだけ読み、完成した行ごとに cb を呼ぶ。
 * 戻り値:  1 = 継続, 0 = 相手が切断, -1 = エラー */
int linebuf_feed(linebuf_t *lb, int fd, line_cb_t cb, void *ctx);

#endif
```

**実験1のデバッグモードを有効にしたまま**動かして、正しく行が組み立てられるようになったら成功。

## 詰まりやすい点

- **`\n` を含まない残りを捨ててしまう。** 次の `recv` と繋げる必要がある。**ここが本質**
- `memcpy` を使う → 領域が重なるので未定義動作。**`memmove` が正しい**
- `recv` が返したバッファを文字列として扱う。**NUL 終端されていない。** 長さを持ち回るか、明示的に終端を置く
- `recv` の第3引数に `sizeof lb->buf` を渡す。正しくは **`sizeof lb->buf - lb->len`**。オーバーフローする。サニタイザを有効にしていれば即座に検出される
- `recv` の戻り値 `0` を「何も来なかった」と解釈する。**`0` は相手が正常に切断したという意味**（エラーは `-1`）

## 完了条件

実験1（1バイトずつ送信）を有効にしたまま、受信側が行を正しく組み立てて表示する。

## 理解度チェック

3. `recv` の戻り値と「送信側が `send` を呼んだ回数」に関係はあるか
4. なぜ 1024 バイトの上限を設けて、超えたら切断するのか。無制限に伸ばすと何が起きるか
5. `memmove` で詰め直す代わりに、読み出し位置を示すインデックスを持つ実装も可能。どちらが良いか

# Session 3: poll で双方向にする（40分）

## この回の1つの大きな考え

> **`poll` は「複数の fd のどれかが準備できるまで待つ」道具。** 標準入力もソケットも同じ fd なので、並べて監視できる。

## まず失敗を体験する（8分）

Session 2 のコードに、素朴に `fgets` で入力を読むループを付ける。

```c
while (1) {
    fgets(line, sizeof line, stdin);   /* ここでブロックする */
    send(fd, line, strlen(line), 0);
    linebuf_feed(&lb, fd, on_line, NULL);
}
```

この状態で**相手側を Ctrl+C で終了させる**。こちらは `fgets` で止まったままなので**何も起きない**。何か打ち込むまで、相手がいなくなったことに気づけない。相手の発言も、こちらが1行打つまで表示されない。

**これが `poll` が必要な理由。**

## 実装する（30分）

```c
#include <poll.h>

struct pollfd pfds[2] = {
    { .fd = STDIN_FILENO, .events = POLLIN },
    { .fd = sock,         .events = POLLIN },
};

for (;;) {
    int rc = poll(pfds, 2, 1000);          /* 1000ms でタイムアウト */
    if (rc < 0) {
        if (errno == EINTR) continue;      /* シグナルで中断。異常ではない */
        perror("poll");
        break;
    }
    if (rc == 0) continue;                 /* 定期処理の置き場（今回は空） */

    /* --- 順序が重要。POLLIN を先に処理する（後述） --- */
    if (pfds[1].revents & POLLIN) {
        /* 相手の発言 */
    }
    if (pfds[0].revents & POLLIN) {
        /* 自分の入力 */
    }
    if (pfds[1].revents & (POLLHUP | POLLERR)) {
        /* 切断 */
        break;
    }
}
```

- [ ] `fgets` を捨て、`poll` ループへ移行する

## 説明

**`events` と `revents` は別物。** `events` は監視したいイベントで自分が設定する。`revents` は実際に起きたイベントで `poll` が設定する。`POLLHUP` / `POLLERR` は `events` に指定しなくても `revents` には現れる。

**タイムアウト引数（第3引数）の意味。** `-1`（無限待ち）にすると、何も届かない間はコードが一切動かない。有限値にすると `rc == 0` の分岐が定期的に回るので、後で PING や持ち時間の更新をそこに置ける。今回は空でよいが、**この分岐は最初から用意しておく**。

**`EINTR` の扱い。** シグナルが届くと `poll` は `-1` / `errno == EINTR` を返す。エラーではないので継続する。見落とすと、ターミナルのリサイズなどで唐突に終了する。

**標準入力にも `linebuf_t` を使うのがコツ。** `fgets` と `read` を混在させると挙動が読みにくくなる。両方を同じ仕組みで扱えば、コードが対称になって理解しやすい。

## 落とし穴: POLLIN と POLLHUP は同時に立つ

**この順序で書くと、読めるはずのデータを捨てる。**

```c
/* ❌ 間違い */
if (pfds[1].revents & (POLLHUP | POLLERR)) break;   /* 先に見て break */
if (pfds[1].revents & POLLIN) { /* ここに到達しない */ }
```

macOS で実測した `revents` の値:

| 監視対象 | `revents` | 内訳 |
|---|---|---|
| パイプ（データあり・書き手が閉じた） | `0x11` | **`POLLIN` + `POLLHUP` が同時** |
| 擬似端末 | `0x01` | `POLLIN` のみ |
| 通常ファイル | `0x01` | `POLLIN` のみ |
| `/dev/null` | `0x20` | **`POLLNVAL`**（poll 非対応） |

「相手が最後の1行を送ってすぐ切断した」場合、`POLLIN` と `POLLHUP` が**同時に**立つ。先に `POLLHUP` を見て `break` すると、**最後の行が読まれずに消える**。

**正しい順序: `POLLIN` を処理してから `POLLHUP` を見る。** 五目並べに移植したとき、この順序を間違えると「相手の最終手や投了が届かない」という形で現れる。

> **デバッグ時の注意**: `./chat < /dev/null` のようにリダイレクトすると、macOS では `/dev/null` に対して `POLLNVAL` が返り、`poll` が即座に返り続ける無限ループになる。標準入力を潰したい場合はパイプ（`echo -n "" | ./chat`）を使う。

## 詰まりやすい点

- `poll` の第2引数は**監視する fd の数**。配列の確保数ではない
- 自分の入力途中に相手の発言が届いて表示が混ざる。今回は気にしない
- `read(0, ...)` が `0` を返すのは EOF（Ctrl+D）。切断と同じ扱いにする

両側から自由に打ち込めて、片方を Ctrl+C で終了させると即座にもう片方が検知して終了する。

# 理解度チェック 解答

**1. `listen` した fd と `accept` が返す fd は何が違うか**

`listen` した fd は**窓口**で、接続要求を受け付けるためだけに存在する。データの送受信はできない。`accept` が返す fd は**個別の通話路**で、特定の相手との間に張られた接続を表す。窓口は開いたままにしておくので、`accept` の戻り値を窓口の変数に上書きしてはいけない（複数の相手を受け付ける場合、窓口を失うと以降の接続を受けられなくなる）。

**2. `AF_UNSPEC` にすると候補が複数返る。全部試す必要があるのはなぜか**

返る候補は「試す価値がある宛先」であって「必ず繋がる宛先」ではない。例えば `localhost` は IPv6 の `::1` と IPv4 の `127.0.0.1` の両方に解決されるが、相手が IPv4 でしか待ち受けていなければ IPv6 側は失敗する。順に試して最初に成功したものを使うのが正しい。1つ目で諦めると環境によって繋がらない。

**3. `recv` の戻り値と「送信側が `send` を呼んだ回数」に関係はあるか**

**無い。** TCP はバイトストリームで、送信側の `send` の区切りは受信側に一切伝わらない。`send` を6回呼んでも `recv` 1回で全部届くこともあれば、`send` 1回でも `recv` が何回にも分かれることもある。届く順序だけが保証される。

**4. なぜ 1024 バイトの上限を設けて、超えたら切断するのか**

上限が無いと、悪意ある（あるいは壊れた）相手が `\n` を1つも含まない大量のデータを送り続けるだけで、こちらのメモリを食い潰せる。これは典型的な DoS の手口。「1行の最大長」を決めて超えたら切断するのが、サーバ側コードの基本的な防御。

**5. `memmove` と読み出しインデックス、どちらが良いか**

**この規模では `memmove` で良い。** バッファが 1024 バイトと小さく、コピーのコストは無視できる。インデックス方式は高速だが、「先頭位置」と「終端位置」の2つを常に正しく保つ必要があり、バグを埋め込みやすい。**まず正しく動く単純な実装を選び、測って遅かったら変える**のが順序。

**6. `poll` のタイムアウトを `-1` にすると、将来ハートビートをどこに書けなくなるか**

`rc == 0`（タイムアウト）の分岐に書けなくなる。`-1` だと何かイベントが起きるまで `poll` から戻ってこないため、「一定時間ごとに実行する処理」を書く場所が無い。定期的な PING の送信、持ち時間のカウントダウン、相手の無応答検知はすべてここに置く。だから最初から有限のタイムアウトにして、空の分岐を用意しておく。

**7. `events` に `POLLHUP` を指定しなくてよいのはなぜか**

`POLLHUP` / `POLLERR` / `POLLNVAL` は「起きたら必ず通知される」種類のイベントだから。`events` は「関心があるものを申告する」ためのフィールドだが、切断やエラーは関心の有無に関わらず知る必要がある。`POLLIN` / `POLLOUT` は明示的に申告しないと通知されない。

**8. `POLLIN` を `POLLHUP` より先に処理しなければならないのはなぜか**

相手が最後のデータを送った直後に切断した場合、`POLLIN` と `POLLHUP` が**同時に**立つ（macOS のパイプで実測: `revents == 0x11`）。先に `POLLHUP` を見て `break` すると、まだバッファに残っている読めるデータを捨てることになる。「切断された = もう読むものが無い」ではなく、「**切断されたが、まだ読めるデータが残っているかもしれない**」が正しい理解。

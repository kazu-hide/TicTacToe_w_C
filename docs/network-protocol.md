# ネットワーク対戦プロトコル v1

9×9 連珠の2人対戦を TCP 上で行うためのプロトコル定義。

関連: [renju-rules.md](renju-rules.md)（ルール解釈）、[network-learning-log.md](network-learning-log.md)（実装の前提知識）

---

## 1. 決定事項

| 項目 | 決定 |
|---|---|
| 通信方式 | P2P。片方が `--host`、もう片方が `--join` |
| 形式 | テキスト、`\n` 区切り、ASCII |
| 先後 | ホストが黒（先手）。`WELCOME` で明示的に通知する |
| ルール判定 | 両側が判定する。受信した手を無条件に信用しない |
| 状態同期 | 着手のみ送る。毎手、盤面ハッシュを添えて照合する |
| メッセージ長 | **128 バイト**（`\n` 込み）。超過はプロトコル違反 |
| 再送 | 行わない。異常は全て切断 |
| ルール解釈 | v1 は「禁じ手 = 打てない手」（[renju-rules.md](renju-rules.md) 3章）。**バージョンに含まれる** |

---

## 2. メッセージ

### 共通形式

```
<VERB> [引数...]\n
```

- 引数の区切りは半角スペース1個
- 大文字小文字を区別する
- `\r\n` も受理する（`\r` は除去）
- 128 バイトを超える行は受理しない

### 一覧

| VERB | 送信者 | 書式 | 意味 |
|---|---|---|---|
| `HELLO` | 双方 | `HELLO <version>` | バージョン申告 |
| `WELCOME` | ホスト | `WELCOME <version> <color>` | 接続側に割り当てる色 |
| `MOVE` | 双方 | `MOVE <row>,<col> <hash>` | 着手 |
| `REJECT` | 双方 | `REJECT <code>` | 受理できない。送信後に切断する |
| `RESIGN` | 双方 | `RESIGN` | 投了 |
| `PING` | 双方 | `PING` | 生存確認 |
| `PONG` | 双方 | `PONG` | `PING` への応答 |

### 引数

| 引数 | 値 |
|---|---|
| `version` | 現在 `1` |
| `color` | `BLACK` または `WHITE` |
| `row` / `col` | `1`〜`9`。**1-origin**（`Board.cells` の添字と一致） |
| `hash` | 盤面ハッシュ。小文字16進8桁 |

### `REJECT` のコード

| コード | 意味 |
|---|---|
| `BAD_FORMAT` | パースできない |
| `UNKNOWN_VERB` | 未知のメッセージ種別 |
| `TOO_LONG` | 128 バイト超過 |
| `VERSION_MISMATCH` | バージョン不一致 |
| `OUT_OF_BOARD` | 座標が盤外 |
| `CELL_OCCUPIED` | 既に石がある |
| `PROHIBITED` | 禁じ手 |
| `NOT_YOUR_TURN` | 手番違反 |
| `HASH_MISMATCH` | 盤面ハッシュ不一致 |

コードは**診断情報**であり、再送を促すものではない。送信側は `REJECT` を送った直後に切断する。

## 3. 盤面ハッシュ

着手を適用した**後**の盤面から計算する。

1. `row` 1→9、`col` 1→9 の順に `cells[row][col]` を走査し、各セルの文字をそのまま連結する（81 バイト）
2. FNV-1a 32bit を適用する

```
h = 2166136261
各バイト b について:
    h = (h XOR b) * 16777619   /* 32bit で切り捨て */
```

3. 小文字16進8桁で表現する（`printf("%08x")`）

暗号学的強度は不要。目的は**偶発的な食い違いの検出**であり、改竄の防止ではない。

## 4. 対局の流れ

```
  join                              host (黒)
    |------- TCP connect ------------->|
    |------- HELLO 1 ----------------->|
    |<------ HELLO 1 ------------------|
    |<------ WELCOME 1 WHITE ----------|
    |                                  |
    |<------ MOVE 5,5 1a2b3c4d --------|   host が先手
    |------- MOVE 5,6 5e6f7a8b ------->|
    |<------ MOVE 6,5 ... -------------|
    ...
```

1. `join` が接続する
2. 双方が即座に `HELLO <version>` を送る
3. ホストは受け取った `version` を検証する
   - 一致 → `WELCOME <version> WHITE` を返す
   - 不一致 → `REJECT VERSION_MISMATCH` を送って切断
4. ホスト（黒）から着手を開始し、以降は交互
5. 受信側は毎回、着手を検証してから適用し、`hash` を自分の計算値と照合する

### 受信時の検証順序

```
1. 128 バイト以内か                → TOO_LONG
2. パースできるか                   → BAD_FORMAT
3. 既知の VERB か                   → UNKNOWN_VERB
4. 自分の手番か                     → NOT_YOUR_TURN
5. 盤内か                           → OUT_OF_BOARD
6. 空点か                           → CELL_OCCUPIED
7. 禁じ手でないか                   → PROHIBITED
8. 着手を適用し、hash が一致するか   → HASH_MISMATCH
```

---

## 5. 終局

**終局を通知するメッセージは無い。** 両側が着手から同じ結論を導く。

| 条件 | 結果 |
|---|---|
| 五連が成立 | 打った側の勝ち |
| `RESIGN` を送信 | 送った側の負け |
| 黒に着手できる空点が無い | 黒の負け（[renju-rules.md](renju-rules.md) 2.1） |
| 白に着手できる空点が無い | 引き分け（同 2.2） |

終局後は双方が `close` する。

---

## 6. 生存確認

`poll` のタイムアウト（1000ms）を刻みとして数える。

| 条件 | 動作 |
|---|---|
| 10 秒間、相手から1バイトも受信していない | `PING` を送る |
| `PING` を受信 | 即座に `PONG` を返す |
| 30 秒間、相手から1バイトも受信していない | 切断する |

「相手が長考している」と「相手が消えた」を区別するための機構。持ち時間はゲームルールであり、ここでは扱わない（8章）。

---

## 7. 異常系

| 事象 | 動作 |
|---|---|
| 検証に失敗（4章の 1〜8） | 該当コードの `REJECT` を送って切断 |
| `REJECT` を受信 | ログに残して切断 |
| 30 秒無応答 | 無言で切断 |
| TCP 切断（FIN / RST） | 相手の異常終了として扱う |

**再送・復旧は一切行わない。** 復旧が必要な場合は再接続（スコープ外）で扱う。

---

## 8. 意図的に含めないもの

| 項目 | 理由 |
|---|---|
| 手番の通知 | 着手が交互なので導出できる |
| 勝敗の通知 | 両側が同じルールで判定するので導出できる |
| 着手の ACK | ターン制では相手の次の着手が事実上の ACK |
| 持ち時間 | ゲームルールであり、プロトコル層ではない |
| 再接続・棋譜の再送 | 別スコープ。導入時は `MOVE` を複数行で送る形にする（1行に詰めない） |
| チャット | 本文に区切り文字が混ざるため、エスケープ設計が必要になる |
| 観戦・マッチング | P2P の範囲を超える |

## 9. 決定の根拠

### なぜ行区切りか

`nc` / `telnet` で叩けることを優先した。プロトコルを設計している最中はこれが速度に直結する。運ぶのが座標と固定コマンドだけなので、**本文に区切り文字が混ざる問題が構造的に起きない**。上限を超えた場合も次の `\n` まで読み飛ばせば同期を回復できる（長さプレフィックス方式は長さフィールドがズレた時点で回復手段が無い）。

固定長も検討した。`MOVE` は行・列・手番の3バイトで足りるので成立するが、後から可変長のデータを載せられないため採用しなかった。

長さプレフィックス方式が現代のプロトコル（gRPC / Kafka / TLS）で選ばれるのは、**中身がバイナリで区切り文字が本文に出るため**であり、速度が主因ではない。本プロトコルは中身をテキストに留める判断をしたので、行区切りが選択肢に残っている。

### なぜ勝敗を送らないか

導出できるものを送ると、**権威を主張する情報源が2つ**できる。食い違ったときにどちらを信じるかという問題が新たに生まれる（HTTP/1.1 が `Content-Length` と `Transfer-Encoding` を両方持ち、解釈の差が request smuggling を生んだのと同じ構図）。

権威を持つ情報源は**着手だけ**とする。

### なぜ盤面ハッシュは例外なのか

ハッシュも盤面から導出できるが、**権威ではなく検証用**である。不一致のとき「どちらが正しいか」を決めるのではなく、両方が止まる。値を主張しないので、上記の問題が起きない。

毎手送るのは、N 手ごとにするとズレてから N 手ぶん進んでしまうため。9×9 の盤面ハッシュは8文字で、秒間1手の通信量では無視できる。

### なぜ不正な手を再送させないか

両側がルールを判定する設計では、**相手は自分の盤面で検証済みの手を送っている**。それが自分の盤面で不正なら、両者の盤面が食い違っている。打ち直させても同じ盤面から同じ手が出るだけで、復旧しない。

`REJECT` が発生すること自体が「同期が壊れた」という事実の証拠である。

### なぜルール解釈をバージョンに含めるか

[renju-rules.md](renju-rules.md) のとおり、RIF ルールは禁じ手を「打つと負ける手」と定義し、本実装は「打てない手」として扱っている。この解釈が相手と違うと、どちらも自分のルールでは正しく動くのに、繋いだ瞬間に食い違う。

```
相手が RIF 解釈  → 黒の三三は合法な自殺手 → 送信してくる
本実装           → 三三は打てない手       → REJECT → 切断
```

バージョンで縛らないと検出できない。

### なぜ 1-origin か

`Board.cells` は `[BOARD_ROWS + 1][BOARD_COLUMNS + 1]` を確保して添字 0 を使わず、UI の入力書式も `5,5` である。プロトコルだけ 0-origin にすると送信時と受信時の2箇所で ±1 が必要になり、片方を落とすと**1マスずれた合法手**になってエラーが出ない。

### なぜ上限が 128 か

現行の最長メッセージは `REJECT CELL_OCCUPIED` の 21 バイト。約6倍の余裕を取った値。

上限は DoS 対策であると同時に、**想定外の入力を早期に検出する仕掛け**でもある。21 バイトのプロトコルで 900 バイトの行を受理する必要はない。

大きいデータ（棋譜の再送など）は1行に詰めず、複数メッセージに分割する方針とする。これにより1メッセージは常に小さいまま保てる。

### なぜ未知の種別で切断するか

HTTP ヘッダや protobuf の unknown fields は無視するのが定石だが、**対局では無視すると状態がズレる**。知らないメッセージが状態に影響するかどうかは、知らない以上判断できない。

バージョン交換で合意しているため、未知の種別が届くのは実装バグか改造クライアントである。

## 10. 実装メモ

- 受信した値を `atoi` でパースしない。エラーを返さないため `"5abc"` を `5` として通してしまう。`strtol` で終端ポインタを確認する
- 行の切り出しは `chat/linebuf.[ch]` をそのまま使う。上限を 1024 から 128 に変更する
- `signal(SIGPIPE, SIG_IGN)` を入れる。相手が閉じた接続への `send` でプロセスが即死する
- `send` は要求より少ないバイト数を返しうる。`chat/main.c` の `send_all` と同じループを使う
- `POLLIN` と `POLLHUP` は同時に立つ。`POLLHUP` は「もう来ない」であって「もう無い」ではないため、`read` が `0` を返すまで抜けない（[network-learning-log.md](network-learning-log.md) 4.2）
